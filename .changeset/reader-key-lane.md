'clawboo': minor
---

A program running beside Clawboo, such as a companion process that watches for approvals, can now make its own background reads behind a sign-in proxy, with a key of its own. Set its public key in `proxyIdentityReaderPublicKey` (or `CLAWBOO_PROXY_IDENTITY_READER_PUBLIC_KEY`), in the same forms the proxy's key takes. It signs a request-bound token for each read in the `clawboo-reader-identity` header, with `iss` `clawboo-reader`, `aud` `clawboo-engine` and a `sub` that starts with `reader:`. Its token reaches a short fixed list of reads and nothing else: `GET /api/system/live`, `GET /api/system/self-version?local=1`, `GET /api/runtimes`, `GET /api/teams`, `GET /api/agents`, `GET /api/tools/approvals?status=pending`, and the event stream and event list narrowed to `approval_requested` and `approval_resolved`, each with an exact query. Anything else answers `403` with `"error": "role"` and `"reason": "reader"`, before the token is spent. Its reads are workspace-wide and never a person's: they set no person, pass no person check, never open the Gateway WebSocket, and need no role, with roles enforced or not. The server refuses to start with the key set and `proxyIdentity` off, or with a key that `proxyIdentityPublicKey` or `CLAWBOO_APP_LINK_PUBLIC_KEY` holds too. `GET /api/access/identity` answers `readerKey`, and the capability flag `auth.readerKey` says the same.

`GET /api/system/live` (and `HEAD`) is new too: it answers `{ "ok": true }` with no access token and no identity token, so a program can tell whether the server is up without signing in. It says nothing else about the install, and has a rate limit of its own, so callers that have not signed in never use up the limit the dashboard shares. The capability flag `system.live` says it is there.

A request-bound identity token is now used once even across a restart: the ids of the tokens each lane accepted (a sign-in proxy's, the app link's and the reader key's) are kept in the database until the token could no longer be accepted, instead of in memory only, where a token used before a restart was accepted once more after it. Tokens issued before the server started are still accepted once. When the database will not take a record, such as on a full disk, the token is checked against memory alone, as before, and the server logs an error.
