Release history of the `clawboo` npm package, newest first. Each entry starts with what changed for you. The full notes for every release are in [`apps/cli/CHANGELOG.md`](https://github.com/clawboo/clawboo/blob/main/apps/cli/CHANGELOG.md), and [Release process](/internals/release-process) explains how a release is made.

<Note>

These docs follow the main branch. The latest npm release is 0.9.0; anything on main that is newer is listed under **Unreleased** once it lands. Run `clawboo --version` to see your version, and `npx clawboo@latest` to run the latest release.

</Note>

<Update label="0.9.0" description="2026-11-17">

0.9.0 turns Home into a working page. Each team can keep goals, KPIs and pages, and Home shows how a team, or all of them, is doing, with every number saying where it came from. Behind a sign-in proxy, an administrator can now let each person's role decide what they may do, let only requests the proxy signed act as a person, and give a program beside Clawboo a key of its own for its reads. The dashboard gets a new frame and a near-black dark mode, and Clawboo now stops the Hermes gateway the way Hermes expects.

**Home**

- **Home is a working page.** It is the first row in the sidebar's nav, and its picker works like the Board's: **All teams**, then each team. Clicking a team in the team rail opens Home on it. A team's Home shows its status line, what needs you, its goals, its KPIs, the requests in flight, spend against its budget, upcoming routines, pinned pages and the files its agents made. **All teams** shows totals, one Needs you list for every team and a card per team. Every number says where it came from: computed from the board, reported by an agent (named, with its run), or typed by a person. See [Home](/using/home).
- **Goals.** Each team can keep goals, each optionally under one parent goal, with an owner, a target date, a status and a health a person sets. A goal's page shows the tasks linked to it, its KPIs, its updates and its cost. A task counts toward a goal when it or its request names one, and progress is done tasks over linked ones. Done and dropped goals fold under the goal list and can be reopened. See [Goals](/using/home#goals).
- **KPIs.** A person defines each KPI once: name, unit, target, period and where its value comes from. Its value can be computed from the board (such as tasks done, spend or run success rate), reported by an agent, or typed by a person. A value older than the KPI allows is marked stale. Agents can suggest a KPI, which a person accepts or dismisses. See [KPIs](/using/home#kpis).
- **Goal updates.** Agents draft updates, and only a person publishes or discards one. A team's Home settings can turn on a weekly team routine that asks the lead to draft an update for each active goal.
- **Pages.** Markdown pages per team, linked to a goal or not, with every revision kept and a way to restore an old one. Agents may write them within limits of their own; a person is never limited. See [Pages](/using/home#pages).
- **A status line.** A sentence made from the board, such as "2 requests in flight, 1 needs you, 3 done this week, $12 of $60 spent". A team can have its lead write it instead, which costs model calls and so is off until a person turns it on. That is not possible with an OpenClaw lead, or a Clawboo Native lead whose board access is read-only (the default) or off. See [The status line](/using/home#the-status-line).
- **Goals on the Board.** Board cards and team chat task cards show the goal a task counts toward, its own or one it inherits from its request. The task drawer, **New task** and a request sent from team chat can pick a goal, and the Board's filter can show one goal's work, or only work toward no goal. See [On the Board](/using/home#on-the-board).

**Behind a sign-in proxy**

- **Roles.** Set `proxyIdentityRoles` to `enforce` (or `CLAWBOO_PROXY_IDENTITY_ROLES=enforce`) together with `proxyIdentity: required`, and the role in each person's identity token decides what they may do. An `owner` sees and does the work, answers approvals, and alone may answer one with "Allow always". An `operator` sets up and runs the install but never answers an approval. A `member` sees and does the work, and answers approvals only when the token says `"approve": true`. A `guest` reaches only the teams the token lists, until its `access_until`. Give the operator role only to people you trust with the server. Roles are off by default. See [Roles](/guides/sso-proxy#roles).
- **Only signed requests act as a person.** Set `personCheck` to `verified` (or `CLAWBOO_PERSON_CHECK=verified`) with the proxy identity lane on, and answering approvals, moving cards, **Retry**, pausing and the other person writes need a token your proxy signed: the dashboard page's own marks no longer count. The same setting opens Clawboo's Gateway WebSocket, and every route of an agent's screen, only for such a person. It is off by default. See [Only signed requests act as a person](/guides/sso-proxy#only-signed-requests-act-as-a-person).
- **Take over only with the proxy's say-so.** With `proxyIdentityControlClaim: required` (or `CLAWBOO_PROXY_IDENTITY_CONTROL_CLAIM=required`), taking over an agent's screen, and every batch of input after, needs a `control` claim naming the agent in a request-bound token. A batch without it hands the screen back to the agent. It is off by default. See [Taking over a screen](/guides/sso-proxy#taking-over-a-screen).
- **A key of its own for a program beside Clawboo.** A program running beside Clawboo, such as one that watches for approvals, can make its own background reads with a key you set in `proxyIdentityReaderPublicKey` (or `CLAWBOO_PROXY_IDENTITY_READER_PUBLIC_KEY`). Its token reaches a short fixed list of reads and nothing else, and it never acts as a person. See [A program beside Clawboo](/guides/sso-proxy#a-program-beside-clawboo).
- **A used token stays used across a restart.** The ids of the request-bound identity tokens Clawboo accepted are kept in its database until the token could no longer be accepted, so a token used before a restart is no longer accepted once more after it.

**The dashboard**

- **A new frame.** An account bar runs along the bottom of the sidebar, with the person a sign-in proxy verified (or "You" on a local install), the theme switch and the Settings gear, which moved there from the agent column. The team rail is 72 px wide with larger icons, and its add-team button sits at the end of the team icons and scrolls with them.
- **A near-black dark mode.** Dark mode moves to a neutral near-black palette on every screen. The brand red, mint and amber stay, and light mode is unchanged.
- **A slim top bar in an app's own window.** An app that shows the dashboard in its own window can set `data-clawboo-embed-titlebar` on the page for a slim top bar: the sidebar's hide button, back and forward through the dashboard's own pages, the team or page name, Needs you and help. In a browser tab, nothing about the top of the page changes. See [Ask for the slim top bar](/guides/app-window#ask-for-the-slim-top-bar).

**Runtimes**

- **Connect this page to OpenClaw.** A dashboard page that was already open when something else connected Clawboo to the OpenClaw Gateway, such as a routine for an OpenClaw agent or OpenClaw opened in another tab, can now connect itself without a reload. OpenClaw's row in **Settings** > **Runtimes** reads **Connected** and offers **Connect this page** beside **Manage** while the page has no Gateway connection of its own, which OpenClaw 1:1 chats need. See [Manage OpenClaw](/runtimes/openclaw#manage-openclaw).
- **Hermes gets its planned stop.** When Clawboo stops, it sends the Hermes gateway SIGINT and gives it up to `CLAWBOO_HERMES_STOP_GRACE_MS` (5 seconds by default, at most 8) to exit before it kills it and its processes. It used to get SIGTERM, which Hermes takes for a crash. `clawboo stop` now waits up to 15 seconds after its SIGTERM (it was 4) before it kills the server. See [The Hermes gateway](/runtimes/hermes#the-hermes-gateway).
- **A runtime follows a moved Node.js.** When the Node.js a runtime Clawboo installed ran on is gone, such as when an app that runs Clawboo on a Node.js of its own is moved or renamed, the runtime now moves to the Node.js Clawboo runs on, when that is the same version or a later release of the same major version on the same kind of processor. On any other Node.js it still reads as not installed until you install it again. See [Which copy Clawboo uses](/operating/data-and-state#which-copy-clawboo-uses).
- **Homebrew upgrades no longer change a runtime's major version.** A runtime installed on Homebrew's `node` formula now names that Node.js by its versioned folder, so a `brew upgrade` to a new major version no longer moves it. A runtime installed this way before keeps the link: install it again after such an upgrade.
- **No Python bytecode from npm.** Connectors started through npm, and the npm that installs a runtime into Clawboo's runtimes folder, now start with `PYTHONDONTWRITEBYTECODE=1`, so a native part's build no longer writes Python `__pycache__` folders into the npm's folder.

**If you script the API**

- **Home routes.** `GET /api/home` reads a team's Home, or the all-teams view, in one read, and the Home API has routes for goals, KPIs, goal updates, pages and Home settings. `POST /api/board`, a person's board patch and a person's team chat message take `goalId`. See [Home API](/reference/rest-api/home).
- **Home tools for agents.** New Tasks MCP tools: `list_goals`, `get_goal`, `list_kpis`, `list_pages` and `read_page` to read, and, when their session is bound to them, `report_kpi`, `suggest_kpi`, `write_page`, `draft_goal_update` and, for the lead, `write_home_summary`. No tool lets an agent publish an update, set a goal's health, define a KPI or change a target. See [Home tools](/reference/mcp-tools#home-tools).
- **A start marker.** The server writes `api-port.json` next to `api-port.txt`, naming its process and version, so a reader can tell a running server from the record of one that crashed. The `clawboo` command checks it before it trusts the recorded port. `api-port.txt` is unchanged. See [Start marker](/reference/configuration#start-marker).
- **Is the server up.** `GET /api/system/live` (and `HEAD`) answers `{ "ok": true }` with no access token and no identity token, and says nothing else about the install. See [The liveness probe](/guides/sso-proxy#the-liveness-probe).
- `GET /api/access/identity` now says whether roles are enforced and what the person may do, and answers `personCheck`, `controlClaim` and `readerKey`. New capability flags: `auth.roles`, `auth.personCheck`, `auth.readerKey`, `computer.controlClaim`, `system.live`, `ui.embedTitlebar` and `home.goals`. See [Feature flags](/reference/rest-api/system#feature-flags).
- Four new event kinds record agent KPI reports, update drafts, publishing and page revisions. See [Home events](/reference/events-and-errors#home-events).

**Fixes**

- A SIGTERM sent while the server was still starting could be taken by one part of the server, so the server kept running and its later stop left the OpenClaw connection open. A SIGINT or SIGTERM sent during the start is now kept, as the shutdown message already was, and runs once the server has started.
- On a start that moves work folders, a stop sent during the start no longer lets the routines resume, and possibly start a run, in the moment before the stop.
- On macOS and Linux, process start times are now read in UTC, so a process that started in the hour a daylight saving change repeats is no longer taken for another one.
- A task that waits on or depends on a task of another team no longer copies that task's title into its own comments, its waiting reason or its team's room.

</Update>

<Update label="0.8.0" description="2026-11-15">

0.8.0 lets an app that runs Clawboo stop it cleanly and open the dashboard from its own notifications. Clawboo now connects to the OpenClaw Gateway only once something needs it, so a Gateway that starts on its first connection can stay asleep. On Linux, each agent can run as an operating system user of its own.

**Run Clawboo from your own app**

- **Stop it over the IPC channel.** An app that runs Clawboo as its own child process can send `{ "type": "shutdown" }` on the channel, and the server stops the way it does on SIGTERM: it ends the agent runs, closes the database and exits with code `0`. This works on Windows too, where a signal ends the process at once. With `CLAWBOO_STOP_ON_DISCONNECT=1`, the server also stops when that channel closes, so it stops with an app that quits or crashes. A server the `clawboo` command starts keeps running after the command returns, as before. See [Start it from your own app](/operating/deployment#start-it-from-your-own-app).
- **Open the dashboard from a notification.** An app that shows the dashboard in its own window can open what one of its notifications is about, through `onOpenTarget` on the object it gives the page: the task's drawer, or **Needs you** with the approval's card brought into view and outlined while it has focus. Before, the app could only bring its window forward. See [Open the dashboard from a notification](/operating/deployment#open-the-dashboard-from-a-notification).

**OpenClaw**

- **The Gateway is left alone until something needs it.** Clawboo connects to the OpenClaw Gateway once there is an OpenClaw agent (or a delete of one still owed to the Gateway), once you open OpenClaw in **Settings** > **Runtimes** or start the Gateway from Clawboo, or once a routine for an OpenClaw agent falls due. An install with OpenClaw agents connects at every start, as before. Until then neither the server, the dashboard nor `clawboo` connects to the Gateway or probes its port, so a Gateway that a service manager starts on its first connection, such as a systemd socket unit on a small Linux machine, stays asleep instead of starting at every boot. See [How Clawboo connects](/runtimes/openclaw#how-clawboo-connects).
- **Not in use, rather than unreachable.** OpenClaw's row reads **Not in use** with **Connect** while nothing uses the Gateway. The welcome screen offers **Open OpenClaw** to bring in the agents of an OpenClaw already set up, **Capabilities** shows no warning for it, [System Health](/using/system-health) passes its Gateway check as "not in use yet", and the dashboard loads with no offline banner.
- `clawboo` no longer prints whether a Gateway answers on port 18789 when it starts.

**A user per agent, on Linux**

- **Each agent can run as an operating system user of its own.** Set `CLAWBOO_AGENT_USERS` to a pool of users you create once (names, or a uid range such as `uid:20001-20008`), `CLAWBOO_AGENT_GROUPS` to a pool of team groups, and `CLAWBOO_WORK_DIR` to a folder of your own. It is used instead of `CLAWBOO_AGENT_USER`, never with it, and is off unless you set it. One agent then cannot read another's sign-ins, sessions or cookies, reach its display or signal its processes. Teammates read and change each other's files in their team's folder, and agents on other teams cannot reach it. See [A user per agent](/operating/agent-isolation#a-user-per-agent).
- **An agent keeps its user for life.** An agent gets the next free user when it is created, and each team gets a group the same way. A deleted agent's processes stop at once, and its user is wiped before another agent gets it. With no free user, a new agent is still created and its runs say why they cannot start; it never falls back to a shared user.
- **Set it up and check it.** `clawboo agent-user plan --pool <n> --teams <m>` prints the setup, with the one sudoers rule a pool needs, and `clawboo agent-user check` checks a pool too. The startup check now also proves, from inside each agent user's own host, that no agent user can list another's home or signal another's process, and refuses a pool whose users share a uid, a primary group or a home.
- **Not available yet with a user per agent:** code tasks that work in a checkout of a repository (refused with the reason), Hermes (it does not start), OpenClaw (not covered, as before), connectors with local reach shared by every agent (they do not start; each agent's own browser does), picking an agent for a Codex or Hermes sign-in on the Runtimes page (give the runtime an API key), a container launcher for a pool, macOS, and copying older agent state in. See [Not available yet with a user per agent](/operating/agent-isolation#not-available-yet-with-a-user-per-agent).

**If you script the API**

- For a Gateway nothing uses, `GET /api/agents` is not `stale`, `GET /api/agents/registry/health` and `GET /api/system/status` report `inUse: false`, and `GET /api/system/idle` reports the Gateway's cron jobs `off` with the reason `not_in_use`. The registry health also reports `configured`. See [Agents API](/reference/rest-api/agents).
- New route: `POST /api/agents/registry/connect`, which the dashboard sends when OpenClaw's row opens.
- With a Gateway set up that nothing used yet, creating an OpenClaw agent or a sync without a body now waits up to about 5 seconds for the connection.

**Fixes**

- A browser connection to the Gateway that fails no longer keeps retrying unseen.
- A reconnect asked for while a Gateway connection was still being made no longer leaves the server unable to connect until it restarts.

</Update>

<Update label="0.7.0" description="2026-11-14">

0.7.0 makes the Board the place where work is tracked and decided, and gives each agent a computer you can watch. Tasks get readable ids such as `MAR-12`, a request you send in chat becomes one main task with its sub-tasks under it, a plan can wait for your OK, and a new **Inbox** shows what needs you and what changed. You can pause an agent, a team or a whole task tree, and Boo Zero can hand work to a team from its own chat. Runtimes now install into a folder Clawboo owns, with no `sudo`, and Hermes runs as the real Hermes through its own gateway. Agents can run as their own operating system user, each task gets a folder of its own, you can watch each agent's browser live, and agents can sign in to websites with a login they are never handed.

**The Board**

- **Readable task ids.** A team's tasks read like `MAR-12`: letters from the team's name, and a number. They show on cards, in the drawer and on task cards in chat, and Find and the Tasks tools take them. You can change the letters in the team's settings until its first task. Existing tasks get theirs on the first start. See [Task ids](/using/board#task-ids).
- **One task per create.** A create sent again from the New task dialog, the Tasks tools or a team chat hand-off returns the same task instead of making a second one, and an agent that hands off the same open work twice under the same parent within 48 hours gets the first task back. An agent cannot hand work back to an agent that is waiting on it, and the hand-off caps now hold in team chat too.
- **Your request is one card.** When a team's lead hands out work for something you asked in chat, your message becomes a main task with every hand-off and plan step nested under it, on the board and in the chat. It waits for its sub-tasks and moves to Done after the lead's summary. To add to a request, comment on its main task; a new message in the chat is a new request. See [Your requests and their sub-tasks](/using/board#your-requests-and-their-sub-tasks).
- **A task that hands out work waits for it.** In team chat, its card reads "Waiting on 3 sub-tasks". When they close, its agent gets one more turn with all their results. A failed sub-task brings the parent to Needs you instead of letting it close as done. Agents can say how a task went with the new `report_result` tool, which never gets a task past a failing check.
- **Plans.** An agent can write a plan as a document on its task, with every revision on the drawer's new **Plan** tab. Turn on **Ask me before splitting work** for a team, and a plan waits in Needs you until you accept it. It is off by default. See [Decide on a plan](/using/board#decide-on-a-plan).
- **Every waiting task says what it waits for.** An agent that blocks a task must give a reason, and Needs you shows it. A task can be assigned to a person, and then no agent takes it. An agent can ask you a question (a choice, a yes or no, or a list of tasks to accept), which parks the task until you answer. You can reopen a finished task. On a local install, "a person" is one built-in person.
- **Agents start when something happens on their task.** Your comment, or a task it waits on finishing, is saved so a restart cannot lose it, and starts the right run once. Agents can start each other with a comment once you allow it: Needs you asks once per job, and after that a job allows 12 wakes an hour, and two agents answering each other stop after 4. A comment from you always wakes the agent. See [What wakes an agent](/concepts/the-board#what-wakes-an-agent).
- **A run's ending is told apart.** An empty reply gets one more turn, then waits in Needs you as **No result** instead of landing in Done. A rate limit, overload or network error goes back to To do and tries again twice. A budget cap or the circuit breaker stopping a run has a status of its own, so neither reads as your Stop.
- **A job cannot run away.** Clawboo counts the runs a job starts by itself. At 100, nothing more starts by itself, and the job's top task shows in Needs you with **Carry on** and **Stop**. Your own messages, **Retry**, replies and **Accept** never count. See [When work restarts by itself](/concepts/the-board#when-work-restarts-by-itself).
- **Labels, and a fair order.** Teams have labels you can set on tasks and filter the board by. Ready tasks go in this order: tasks that ran and came back, then priority, then oldest first. A task that keeps waiting moves up one priority every 4 hours, up to **High**. Agents, and scripts other than the dashboard, can set a priority of **High** at most: **Urgent** is a person's call.

**Inbox and pause**

- **Inbox.** The sidebar has an **Inbox** with **Unread**, **Needs you**, **Mine** and **All**, and a badge that counts what needs you and what changed. What you do yourself does not make a task unread for you. Read state is kept on the server, so it is the same in every browser, and behind a sign-in proxy each person has their own. See [See it all in the Inbox](/using/board#see-it-all-in-the-inbox).
- **Pause an agent, a team or a task tree.** Use **Pause** in an agent's or a team chat's header, in a task's drawer, or from a right-click on the team rail or the Org chart. A pause holds until you resume it, through a restart. Its runs stop within seconds, and nothing it covers starts: no task, no Routine and no wake. A routine that falls due during a pause runs once on resume. A one-to-one chat with an OpenClaw agent runs in the Gateway, so a pause does not cover it. See [Pause work](/using/board#pause-work).
- **Archived teams stop.** An archived team's agents stop working, and nothing wakes them until you bring the team back. Before, work left on its board kept starting.
- **A person goes first.** When every run slot is taken, a person's chat turn goes first, then tasks by priority, so an **Urgent** task is no longer stuck behind everything queued before it.

**Boo Zero**

- **Hand work to a team from Boo Zero's chat.** Start a message with **@Team**, or say which team in plain words, and each hand-off becomes a task on that team's board, with its card in both chats. The result comes back to Boo Zero's chat, even across a restart. This works when Boo Zero runs on Clawboo Native, Claude Code, Codex or Hermes; an OpenClaw Boo Zero cannot hand off from its chat, and says so. See [Give a team work from this chat](/using/boo-zero#give-a-team-work-from-this-chat).
- **Boo Zero asks before picking a team you did not name.** Work starts at once only on a team your message names. A hand-off to any other team waits on a card in the chat, and nothing starts until you press **Accept**.
- **Words that are not yours are marked.** What an `@Team` message pulls in, Boo Zero's saved notes, and results kept since a Stop reach Boo Zero quoted, under who wrote them. On Clawboo Native, Claude Code, Codex and Hermes, a one-to-one chat gets only `get_task`, `list_tasks` and `add_comment` on the board.

**Agent computers**

- **Watch each agent's browser live.** The **Browser** card on an agent's page shows its browser live, and falls back to the last screenshot when no browser is open. On macOS and Windows, and on Linux without `Xvnc`, the view shows the browser about once a second, for watching only. See [Watch a screen and take over](/using/agents#watch-a-screen-and-take-over).
- **A screen for each agent on Linux.** With TigerVNC's `Xvnc` on the server, each agent's browser opens on a virtual screen of its own. **Take over** sends your mouse and keys to it while the agent's browser tools wait, until you **Hand back**. The agent's other programs share that screen, so type a password there only for an agent you trust. The screen listens on no network port. All agents share one agent user, so this keeps displays from other users on the machine, not agents from each other.
- **Install the desktop tools.** On Linux, **Install the desktop tools** on an agent's **Screen** view installs TigerVNC's `Xvnc` (x86_64 only) and Cua Driver into Clawboo's runtimes folder, each checked against a SHA-256 Clawboo pins. Clawboo's copy of `Xvnc` needs some system libraries that Clawboo does not install, and the **Screen** view names any that is missing. Cua Driver, a new connector, lets an agent use the apps on its own screen. It runs only when agents run as their own user, and only for the agents you give it to. See [Connectors](/using/connectors).
- **Share a screen with a link.** A **view link** lets someone with no way into your Clawboo watch one agent's screen. A **control link**, for example for a person who must type their own password into a site, is offered only when agents run as their own user. A view link expires after 8 hours and a control link after 1 hour by default. You can revoke either, and a restart revokes them all.
- **The Computer tab.** The tab on an agent's page that showed its files is now **Computer**, with **Screen** and **Files**. It lists the agent's task folders beside its worktrees.
- **A folder for each task.** A task run with no git worktree now starts in a folder of its own, `~/clawboo-work/teams/<team id>/tasks/<task id>` by default, instead of the team's shared folder, so a file stays with the task that made it. - Google agents on Clawboo Native start on `gemini-3.6-flash`; Google shut down `gemini-2.0-flash` on 2026-06-01. Multi-step tool turns on Gemini 3 keep their thought signatures. Anthropic runs on Clawboo Native, direct or through OpenRouter, use prompt caching, and cached tokens are priced at the cache rates. See [Clawboo Native](/runtimes/native#costs).
- Connecting OpenClaw with a Google key sets `google/gemini-3.6-flash` as the default model, and the OpenClaw model picker lists Gemini 3.6 Flash in place of Gemini 2.0 Flash. A default an earlier version set is kept: change it under **Manage > Default model**. See [OpenClaw](/runtimes/openclaw).
- Cleaning up connector processes a crashed server left running no longer risks stopping an unrelated process. Inside a container, a restart kept the host's boot time, so a process id recorded before the restart could name another process. Each record now names its PID namespace and when that namespace's first process started, and a process whose start time cannot be read is left running and checked again at the next start. Agent processes recorded before a container restart are never stopped either.
- A team can have a verify command that every check runs, set under **Work check** in the team's settings or with `PUT /api/team-verify-command/:teamId`, and each check records where its command came from: the task drawer flags one the agent wrote itself. A review that failed or returned nothing reads **Review did not complete** or **Review returned nothing** instead of **Reviewed by**. See [How work is checked](/concepts/verification#the-verify-command-in-practice).
- Claude Code reads as installed exactly when the Claude Agent SDK and its own `claude` binary sit next to Clawboo, because every run loads the SDK and starts that binary. A `claude` CLI on its own no longer reads as ready while its runs fail, and **Install** fetches the SDK (`@anthropic-ai/claude-agent-sdk@0.3`) instead of the CLI; from `npx` or a source checkout it says what to run instead.
- Routines run in a time zone you choose, one for every routine on the install and independent of the server process. The routine dialog names it under **Runs**, with **Change** to pick another, and a change moves every routine's next run to the new zone. It starts as the server's zone, so nothing changes until you pick one. A server in a container, which runs in UTC unless `TZ` is set, can now run a 9:00 routine at 9:00 your time. A `once@` time typed in the dialog needs a `Z` or an offset.
- Connectors and the shell commands you approve keep npm's prefix, cache and update-check settings (never an npm credential), so an approved `npm install -g` works on a server whose npm prefix points at a folder of its own. Connectors also start with npm's update check off.

**Running Clawboo for a team**

- **Pin settings for everyone.** Admins who deploy Clawboo for a team can pin settings in one file, `~/.clawboo/operator.json` or the file `CLAWBOO_OPERATOR_SETTINGS` names, or with each key's environment variable. **Settings** > **System** > **Deployment** shows a pinned setting as "Set by your administrator". A file Clawboo cannot trust stops the server at startup, and the file never holds secrets. See [Pin settings for everyone](/operating/deployment#pin-settings-for-everyone).
- **Turn the dashboard's updates off.** `CLAWBOO_DISABLE_SELF_UPDATE=1` removes the update chip, stops the npm check and refuses the in-app update. Without it, a global install the server's user cannot write, such as a root-owned `/usr/local`, is no longer offered the one-click update, which could only fail there.
- **Keep the browsers from starting.** `CLAWBOO_DISABLE_BROWSER_AUTOSTART=1`, or the switch in **Settings** > **System** > **Deployment**, stops Playwright and Chrome DevTools starting on a new install. When the pinned version is already installed, each browser now starts from that copy instead of through `npx`, which kept an `npm exec` process running beside it and asked the registry on every start. Chrome DevTools runs with its usage statistics and update check off.
- **A release reads its own catalog.** The Marketplace catalog comes from the release's tag on GitHub instead of the `main` branch, so content written for a newer version no longer reaches an older install. A development build still reads `main`.
- **Updates keep node options.** After an update from the chip, the server restarts with the node options it was started with, such as `--max-old-space-size`.

</Update>
