Use this page when you want to change Clawboo and open a pull request. It walks the contributor workflow and links into the rest of the docs. The repo's [`CONTRIBUTING.md`](https://github.com/clawboo/clawboo/blob/main/CONTRIBUTING.md) is the authority on process: if the two disagree, `CONTRIBUTING.md` and the root `package.json` win. Why the code is shaped the way it is lives in the [contributor overview](/internals/index).

## Before you begin

- **Node.js 22.12 or later** and **pnpm 9**. The root `package.json` declares `engines.node >=22.12.0` and `engines.pnpm >=9.0.0`, and pins `pnpm@9.15.0` as its package manager.
- **No external runtime.** Clawboo Native runs agents inside the server, with a provider key or a local Ollama. Install OpenClaw, Claude Code, Codex or Hermes only when you work on that runtime.

## Make a change

<Steps>
<Step title="Clone and install">

```bash
git clone https://github.com/clawboo/clawboo.git
cd clawboo
corepack enable
pnpm install
```

`corepack enable` makes `pnpm` the pinned 9.15.0, which keeps lockfile diffs clean. `pnpm install` links the whole workspace: `packages/*`, `packages/adapters/*`, `apps/*` and `docs` (see [Monorepo and build](/internals/monorepo-and-build)).

</Step>
<Step title="Run the dev stack">

```bash
pnpm dev
```

The dashboard's dev orchestrator picks a free API port first, then starts the Express API and the Vite dev server with that port in their environment, so the UI's proxy and the API always agree. It prints a banner like this:

```text
[clawboo-dev] API port: 18790  ·  UI port: 5173
```

- The **Vite SPA** serves on port 5173.
- The **API** takes the first free port from 18790 to 18809. Pin it with `CLAWBOO_API_PORT` (see [Environment variables](/reference/environment-variables)).
- `pnpm dev` also starts the docs preview (`mint dev --port 3111`), which needs the Mintlify CLI.

Clawboo keeps its state in `~/.clawboo/`, created on first run. Set `CLAWBOO_HOME` to point a dev instance at a throwaway directory. There are no feature flags: every subsystem is on. Budgets track spend and warn, and nothing pauses a run until someone sets a hard cap.

</Step>
<Step title="Work on a branch">

Clawboo follows [GitHub Flow](https://docs.github.com/en/get-started/using-git/github-flow): branch from `main`, push, open a pull request, and squash-merge once CI is green. Name the branch with a prefix:

| Prefix      | For                          |
| ----------- | ---------------------------- |
| `feat/`     | A new feature or surface     |
| `fix/`      | A bug fix                    |
| `chore/`    | Tooling, deps, housekeeping  |
| `docs/`     | Documentation only           |
| `test/`     | Tests only                   |
| `refactor/` | Non-behavioral restructuring |

</Step>
<Step title="Run the local gate">

These are the checks CI runs, as root scripts:

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm e2e
pnpm catalog:verify
pnpm verify:connectors
pnpm assemble && pnpm test:clean-install
```

- **`pnpm format:check`** runs Prettier; fix failures with `pnpm format`. CI's Lint job runs it before `pnpm lint`.
- **`pnpm lint`** runs ESLint across the workspace, the docs frontmatter and heading check, and `scripts/`.
- **`pnpm test`** runs every package's Vitest suites, including `apps/web`'s node project (`*.test.ts`) and jsdom project (`*.test.tsx`, with React Testing Library, msw, jest-dom and jest-axe). CI runs the same suites as `pnpm test:coverage`, which adds a coverage table and no threshold.
- **`pnpm e2e`** runs Playwright in a sandboxed `$HOME`. It needs `pnpm build` first and a Chromium download (`pnpm exec playwright install chromium`).
- **`pnpm catalog:verify`** checks every marketplace content rule, then that `catalog/dist` and the compiled seed match a rebuild. **`pnpm verify:connectors`** checks the committed connector catalog. Both are offline.
- **`pnpm assemble && pnpm test:clean-install`** bundles the CLI, packs and installs the tarball in a temp directory, and boots that install, through a headless-Chromium check and one real agent run. It needs network access for its `npm install`, the same Chromium download, and no other Clawboo dashboard on ports 18790 to 18809 (stop `pnpm dev` first).

`pnpm prepublish:check` runs the catalog and connector gates, then `pnpm assemble` and `pnpm test:clean-install`. [Testing](/internals/testing) lists every CI job, including the cross-platform tests and the website build that have no single local command.

</Step>
<Step title="Add a changeset">

Clawboo uses [Changesets](https://github.com/changesets/changesets) for versions and changelogs:

```bash
pnpm changeset
```

Choose the `clawboo` package and a bump (`patch`, `minor` or `major`), write a short summary, and commit the new file under `.changeset/`. Every `@clawboo/*` library is private and only `clawboo` publishes, but the dashboard (`apps/web`) ships inside it. So add a changeset for any change a user of the npm package would notice, dashboard changes included. Docs-only, CI-only and test-only changes need none. [Release process](/internals/release-process) has the details.

</Step>
<Step title="Open the pull request">

Push the branch and open a pull request; the template walks the checklist. Keep one concern per pull request, add a test for what you add (Vitest for logic, the jsdom project for components, Playwright for new end-to-end behavior), and get CI green before you ask for review. Pull requests are squash-merged into `main`.

Keep the `pnpm-lock.yaml` diff small. If it grows by thousands of lines, you are on a different pnpm: run `corepack enable`, then `pnpm install`, and commit only the intended change. Dependabot opens grouped dependency updates weekly, so you rarely need to touch the lockfile by hand.

</Step>
</Steps>

## Your first contribution

Issues labeled [`good first issue`](https://github.com/clawboo/clawboo/labels/good%20first%20issue) are scoped small and name the files to touch. Comment on the one you want and a maintainer assigns it to you. Good areas that rarely need core changes: a marketplace team template, a docs page, a provider or runtime icon, or a test for an uncovered component. If you are unsure whether an idea fits, open a [Discussion](https://github.com/clawboo/clawboo/discussions) before you write code. A half-finished pull request with a question is welcome.

## Documentation changes

The `docs/` directory is this site: hand-edited Mintlify pages with no build step. Merging to `main` redeploys [docs.claw.boo](https://docs.claw.boo) as it is, so the files in your diff are exactly what ships.

<Warning>
  Two mistakes break a page. Quote any frontmatter `title` or `description` that contains `: ` or
  starts with `@` or a backtick, or Mintlify serves the page as a 404. Never put a bare `%` in a
  heading, or the page fails to build its anchors.
</Warning>

`pnpm check:docs` catches both, and it also runs inside `pnpm lint` and CI's Lint job. For a full check, use the Mintlify CLI: `npx mint validate` runs a strict build, and `npx mint broken-links --check-anchors` checks links and anchors. Mintlify keeps `/` and quote characters in heading anchors, so link to the page rather than to a heading that contains them. [`docs/README.md`](https://github.com/clawboo/clawboo/blob/main/docs/README.md) covers the layout, the hand-maintained `docs.json` navigation and local preview.

## Contributing a marketplace pack

Agent and team content lives in `catalog/`, a plain content folder outside the workspace. Edit `catalog/packs/<publisher>/<slug>/**`, run `pnpm catalog:build` to regenerate `catalog/dist` and the compiled seed, run `pnpm catalog:verify`, and commit the regenerated `catalog/dist/**` with your change. A pull request that touches only `catalog/` runs the short `catalog-ci.yml` instead of the full matrix, except for `catalog/packs/clawboo/**` (the seed compiled into the npm package), which gets the full matrix.

Packs are reviewed as writing and merged by hand. `CONTRIBUTING.md` has the review bar: a description is one or two sentences, `IDENTITY.md` is the full instruction body, a pack with `provenance.repo` ships a `NOTICE.md`, a team has at least two members, and new categories are declared. The format is in the [marketplace catalog reference](/reference/marketplace-catalog).

## Code guidelines

Review and, where possible, lint enforce these:

- **TypeScript strict.** No `any`, no `@ts-ignore`, no leaking `unknown`.
- **No `console.log`.** Log through [`@clawboo/logger`](/reference/packages/index#logger) (pino).
- **Lucide icons only**, never emoji in the UI.
- **Theme tokens, never raw hex.** Use the CSS variables and Tailwind tokens; brand marks are the only exception. See the [design system](/internals/design-system).
- **Keep new database columns addable.** There is no migration ladder; [Schema changes](/internals/monorepo-and-build#schema-changes) lists the rules a new column must meet.
- **Version every persisted client store.** A zustand `persist` store sets both `version` and `migrate`, and the migrate is a pure exported function with its own test.
- **Pollers pause when the tab is hidden.** A new interval refresh uses `useVisiblePolling` from `apps/web/src/lib/useVisiblePolling.ts`, not a bare `setInterval`.
- **Schema fixtures are append-only.** Never edit `packages/pack-format/src/__fixtures__/v1/*.json`; a changed shape gets a fixture under the new version's folder. Each version has a `minimal.json` and a `kitchen-sink.json` that sets every optional field.
- **Pure where it claims to be.** Policy and projection functions stay free of side effects and unit-testable.
- **No secrets in logs, responses or storage.** Show that a credential is present (the env var name and true or false), never its value. See [Security](/operating/security).

## Architecture rules

A change must keep the [architecture invariants](/internals/architecture-invariants). The ones a first contribution is most likely to meet:

- **The agent registry says who exists; the OpenClaw Gateway says how OpenClaw agents run.** Read agents through an [`AgentSource`](/internals/agent-source), not straight off the Gateway client.
- **Packages never import apps.** Dependencies flow one way: `apps/web` imports `packages/**`, and the adapters import `@clawboo/executor`. Lint enforces it; see [Monorepo and build](/internals/monorepo-and-build).
- **Every runtime is a [`RuntimeAdapter`](/internals/runtime-adapter).** A new runtime implements the trait and emits the normalized `RuntimeEvent` stream instead of adding special cases to the orchestrator.
- **The board is the record for task and coordination state.** Prefer board changes over parsing prose; see [Board internals](/internals/board-internals).
- **Schema changes are additive.** An upgrade only adds missing columns. It never removes a column or changes one's type or constraints, so those are not in-place upgrades.

The [contributor overview](/internals/index#caution-surfaces) lists the caution surfaces: files that hold a rule whose breakage shows up far from the edit. Read the linked page before you change one.

## Releases

Releases are automated and maintainer-only. When a changeset lands on `main`, `publish.yml` opens a pull request titled `chore: version packages`. Merging it bumps the version, updates the changelog and publishes the `clawboo` package to npm; nothing else publishes, and nobody runs `npm publish` by hand. Before it publishes, the workflow reruns the build, lint, typecheck, tests, the catalog gate and the clean-install gate. It does not rerun every pull request check, and it needs the network. See [Release process](/internals/release-process).
